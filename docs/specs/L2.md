# L2 - Detailed Requirements

## L2-001: Browser Capability Detection & Unsupported Browser Fallback
**Traces to:** L1-001

On initial application load, the system shall synchronously probe browser support for Chrome built-in Gemini Nano APIs, WebGPU, Web Bluetooth, and WebAssembly. When WebGPU, Web Bluetooth, and Gemini Nano are unavailable, the system shall route the user to `/unsupported`, displaying per-capability status indicators and offering a path to continue in WebAssembly CPU mode.

**Acceptance Criteria:**
1. Given a browser lacking Gemini Nano, WebGPU, and Web Bluetooth with WebAssembly available, when the user loads the application, then the system routes to `/unsupported` and displays `Built-in Gemini Nano: Unavailable`, `Web Bluetooth: Unavailable`, and `WebAssembly CPU fallback: Available`.
2. Given the user is on `/unsupported`, when the user activates `Continue in WASM mode`, then the system switches the active backend to WebAssembly CPU mode and navigates to `/lab` in the WebAssembly state.
3. Given the user is on `/unsupported`, when the user activates `Back to Today`, then the system navigates to `/`.

---

## L2-002: First-Run Onboarding Flow
**Traces to:** L1-001

First-time users with no saved local profile shall be guided through `/welcome` without requiring account creation or authentication. The flow shall present a three-step progress stepper (`Browser check`, `Your rhythm`, `Ready`), display detected Gemini Nano and WebGPU readiness, collect a required display name and a weekly movement focus (`Strength & mobility`, `Running & endurance`, or `Gentle daily habit`), and allow skipping setup.

**Acceptance Criteria:**
1. Given a first-run user on `/welcome` while capability checks are running, when the page initializes, then the system displays a loading state (`Setting up Haloop`) until probing completes.
2. Given the onboarding form is displayed, when the user submits with an empty or whitespace-only display name, then the system prevents submission, displays a top error summary (`Check your details`), and displays an inline field error prompting for a display name.
3. Given the user enters a valid display name and selects a weekly movement focus, when the user activates `Continue`, then the system persists the profile locally and renders the completion state greeting the user by name with `Open Today` and `Review AI Lab` actions.
4. Given the user is on `/welcome`, when the user activates `Skip for now`, then the system navigates directly to `/` without blocking access.

---

## L2-003: Onboarding Local Storage Initialization Error Handling
**Traces to:** L1-001

When browser storage cannot be initialized during onboarding (such as in a private browsing window where persistent model caches are blocked), the system shall display a recoverable error state explaining the restriction.

**Acceptance Criteria:**
1. Given persistent local storage or OPFS initialization throws an error during `/welcome`, when onboarding loads, then the system displays `Could not initialize local storage` explaining that private browsing windows cannot persist model caches and provides a `Try again` action.
2. Given the onboarding storage error state is displayed, when the user activates `Try again`, then the system re-attempts local storage initialization.

## L2-004: Persistent Application Shell & Primary Navigation
**Traces to:** L1-002

All in-app pages (`/`, `/train`, `/coach`, `/history`, `/history/:id`, `/devices`, `/lab`, `/settings`, `/offline`, `/404`) shall render inside a consistent application shell providing navigation across the seven primary sections, active-route indication, and live sidebar status indicators for linked Bluetooth devices and on-device AI/offline status.

**Acceptance Criteria:**
1. Given an authenticated-free local session on any primary route, when the shell renders, then navigation links for `Today`, `Train`, `Coach`, `History`, `Devices`, `AI Lab`, and `Settings` are present and the active section link carries `aria-current="page"`.
2. Given the user views `/history/:id`, when the shell renders, then the `History` navigation item carries `aria-current="page"`.
3. Given two Bluetooth devices are linked and Gemini Nano is active, when the desktop sidebar renders, then the sidebar footer displays `2 devices linked` and `Gemini Nano on-device` (or `Offline · N models cached` when offline).
4. Given a desktop viewport (`>= 992px`), when the user scrolls the main content vertically, then the left rail (`.app-sidebar`) stays pinned to the viewport (`top: 0`, `height: 100dvh`, `overflow: hidden`) and never vertically scrolls.

## L2-005: Global System Status Banners
**Traces to:** L1-002

The application shell shall surface top-level system status banners for cross-cutting runtime conditions: offline mode (`info`), reconnection (`success`), CPU WebAssembly fallback (`warning`), near-full storage (`danger`), and disabled Chrome built-in AI flags (`persistent`).

**Acceptance Criteria:**
1. Given the browser transitions offline with cached models available, when any in-app page is viewed, then an `info` banner displays the offline status and cached model readiness with a `Details` link to `/offline`.
2. Given the browser regains connectivity while Hugging Face downloads were paused, when connectivity is restored, then a `success` banner informs the user that downloads can resume with an `Open AI Lab` action.
3. Given WebGPU is unavailable in the active browser window, when the user runs in CPU fallback mode, then a `warning` banner states `Running on CPU via WebAssembly` with a `Learn more` link.
4. Given local cache usage reaches or exceeds 90% of the configured model cache budget, when the user views the app, then a `danger` banner warns that new sessions risk failing to save and provides a `Manage cache` action linking to `/lab`.
5. Given the Chrome `Writer & Rewriter` flag is disabled, when the user views `Today`, then a `persistent` banner offers an `Enable flag` action opening the Chrome flags guide dialog.

## L2-006: In-Shell Not-Found (404) Route Handling
**Traces to:** L1-002

Any unrecognized application route or request for a non-existent session identifier shall render the `/404` page inside the application shell with recovery links.

**Acceptance Criteria:**
1. Given the user navigates to an unregistered path or a non-existent `/history/:id`, when routing resolves, then the system renders `We couldn't find that page` inside the application shell without fetching remote data.
2. Given the `/404` page is displayed, when the user activates `Go to Today` or `View History`, then the system navigates to `/` or `/history` respectively.

## L2-009: Active Workout Studio & Local Pose Estimation
**Traces to:** L1-004

The `/train` route shall run live workouts using `onnx-community/vitpose-base-simple` over the local camera feed to count repetitions and calculate real-time form scores, while displaying a local-privacy indicator (`Camera local · never uploaded`), current movement and set progress, live rep count (`completed / target`), elapsed timer, real-time coaching cues (spoken via `Kokoro-82M-ONNX` when enabled), hands-free voice command status (`whisper-base`, e.g., `"Next set" ready`), and live telemetry cards (`Heart rate` with zone, `Cadence`, and `Up next`).

**Acceptance Criteria:**
1. Given camera permission is granted and VitPose is cached, when a workout session is active on `/train`, then the camera stage displays `Camera local · never uploaded`, current exercise name, live rep count, form score percentage, elapsed time, and coaching cue text.
2. Given a Bluetooth heart-rate sensor is connected during an active session, when live telemetry arrives, then the camera HUD and Heart rate KPI card update with the current bpm and heart-rate zone.
3. Given Kokoro TTS is enabled in Settings and cached, when a coaching cue is triggered during an active session, then the system synthesizes and plays audio locally without network requests.
4. Given Whisper is cached and microphone permission is granted, when the user speaks a supported command (such as "Next set" or "Pause"), then the system executes the corresponding workout state transition locally.

**Traces to:** L1-004

The `/train` route shall explicitly manage model warm-up loading, pre-workout idle selection, paused session state, and blocked camera permission with audio-only fallback.

## L2-011: Finish Workout Confirmation & Local Persistence Dialog
**Traces to:** L1-004

Activating `Finish session` or `Finish & save` on `/train` shall open the modal `Finish workout?` dialog summarizing elapsed time, total reps, and form score, allowing an optional devotional or training note (maximum 280 characters), and saving the completed session to local IndexedDB.

**Acceptance Criteria:**
1. Given an active or paused session on `/train`, when the user activates `Finish session`, then the modal `Finish workout?` dialog opens with elapsed duration, total reps, form score, an optional reflection textarea, `Keep training`, and `Save session`.
2. Given the user enters a reflection note exceeding 280 characters, when the user submits `Save session`, then the dialog stays open, prevents persistence, and displays an inline validation error (`Keep your reflection note under 280 characters`) with the current character count.
3. Given valid session data is submitted, when IndexedDB persistence is in progress, then `Save session` transitions to a disabled `Saving…` busy state preventing duplicate writes.
4. Given local storage quota is full during save, when persistence fails, then the dialog displays `Could not save session` with guidance to free space in AI Lab and a retry action without discarding the user's reflection note.
5. Given persistence succeeds, when the write commits, then the dialog closes and the system navigates to the newly created `/history/:id` session detail view.

## L2-012: On-Device AI Coach Conversation
**Traces to:** L1-005

The `/coach` route shall provide a conversational interface powered by Chrome's built-in Gemini Nano Prompt API (falling back to cached `onnx-community/Qwen2.5-0.5B-Instruct` when Gemini Nano is unavailable), displaying an `On-device · Private` badge, chronological message thread with timestamps, streaming/submitting feedback, and contextual action buttons (such as applying a workout adjustment to `/train` or opening Scripture translation/search).

**Acceptance Criteria:**
1. Given Chrome Gemini Nano Prompt API (or cached Qwen2.5-0.5B fallback) is available, when the user submits a non-empty message in the Coach composer, then the user message appends to the thread, the composer disables submission displaying `Sending` and `Generating on-device…`, and the assistant response renders locally.
2. Given the Coach generates a workout modification suggestion or Scripture reference, when the reply renders, then contextual action controls (such as `Apply light-load warm-up` or `Translate verse`) are keyboard-accessible and route to `/train` or the Scripture search/translation flow.
3. Given the composer input is empty or whitespace-only, when the user attempts to submit, then the system blocks submission and preserves focus in the input field.

## L2-014: On-Device Semantic Scripture Search & Translation
**Traces to:** L1-005

Activating `Search Scripture` from `/coach` shall open a modal dialog running semantic vector search over the cached KJV index using `Xenova/all-MiniLM-L6-v2` in a Web Worker, returning ranked KJV verses with an `Insert` action and supporting on-device translation across 12 languages via Chrome's built-in Translator API.

**Acceptance Criteria:**
1. Given `Xenova/all-MiniLM-L6-v2` is cached, when the user submits a non-empty theme, keyword, or verse reference in `Search Scripture`, then the dialog enters a `busy` state while computing embeddings and renders matching KJV references and excerpts with an `Insert` button per result.
2. Given the user submits an empty or whitespace-only query, when search is triggered, then the dialog displays an inline validation message (`Enter a theme, keyword, or reference (for example, "patience" or "Psalm 23")`).
3. Given a verse result is displayed, when the user activates `Insert`, then the selected verse reference and text are inserted into the Coach conversation context and the dialog closes.
4. Given a non-English Scripture language is selected from the 12 supported languages and Chrome's Translator API is available, when Scripture is rendered or translated, then translation executes locally via Chrome's Translator API with zero remote network calls.

4. Given WebGPU is unavailable, when `/lab` renders, then the page displays a `Running on CPU via WebAssembly` notice while keeping all open model controls operational.

## L2-026: Storage Quota & Integrity Resilience
**Traces to:** L1-010

The system shall monitor browser storage quota and handle IndexedDB locks, quota exhaustion, private browsing restrictions, and corrupted records without silent data loss or unhandled exceptions.

**Acceptance Criteria:**
1. Given browser storage usage exceeds 90% of the configured budget, when the user navigates within the app, then the system surfaces the storage-nearly-full `danger` banner with a direct link to `/lab`.
2. Given an IndexedDB write fails with `QuotaExceededError` or a read fails due to a corrupted record, when the error is caught, then the UI presents a human-readable recovery message and preserves unsaved user input in memory so the user can retry after freeing space.

## L2-027: Zero Cloud Relay & Local Data Containment
**Traces to:** L1-011

The system shall never transmit camera frames, microphone audio, Web Bluetooth biometric streams, Coach prompts or responses, Scripture notes, or workout history to any remote server.

**Acceptance Criteria:**
1. Given an active workout session with camera, microphone, and Bluetooth HR streaming, when network traffic is inspected over the entire session and save flow, then zero outbound HTTP/WebSocket/WebRTC requests containing media, telemetry, or user data are sent.
2. Given a Coach conversation and semantic Scripture search with models already cached, when the user sends prompts and searches verses, then zero outbound network requests occur.
3. Given the user explicitly clicks `Download` on an uncached Hugging Face model in `/lab`, when network traffic is inspected, then outbound requests are restricted strictly to fetching the selected model artifacts from Hugging Face.

---

## L2-028: Input Validation, Output Sanitization & XSS Prevention
**Traces to:** L1-011

All user-entered text (`Display name`, workout reflection notes, Coach messages, History and Scripture search queries, Bluetooth `Device label`) and all on-device AI outputs shall be validated for type/length bounds and rendered strictly as escaped text to prevent DOM XSS and injection attacks.

**Acceptance Criteria:**
1. Given a user enters HTML or script payloads (e.g., `<script>alert(1)</script>` or `<img src=x onerror=alert(1)>`) into Display name, reflection notes, Coach chat, search inputs, or Device label, when saved and rendered across Today, History, Session Detail, Coach, or Devices, then the payload renders strictly as literal text and zero scripts execute.
2. Given the application is served, when HTTP response headers or meta policies are inspected, then a strict Content Security Policy (CSP) blocks inline script execution and restricts `connect-src` to `'self'` and authorized Hugging Face model hosts.

---

## L2-029: Browser Hardware Permission Isolation & Safe External Links
**Traces to:** L1-011

The system shall request camera, microphone, and Web Bluetooth permissions exclusively in response to explicit user actions, degrade safely when permissions are denied or revoked mid-session, and secure all external links against tabnabbing.

**Acceptance Criteria:**
1. Given a user loads `/` or `/welcome` without initiating a workout or device pairing, when the page initializes, then the system triggers zero browser permission prompts for camera, microphone, or Bluetooth.
2. Given camera or Bluetooth permission is revoked while on `/train` or `/devices`, when the revocation is detected, then the system stops the affected hardware stream cleanly and transitions to the corresponding error/fallback state without crashing.
3. Given external Hugging Face model repository links on `/lab`, when rendered in the DOM, then each link with `target="_blank"` includes `rel="noreferrer"` (or `rel="noopener noreferrer"`).

## L2-030: Non-Blocking Web Worker ML Execution & Real-Time Pose Performance
**Traces to:** L1-012

All Hugging Face Transformers.js inference pipelines (`vitpose-base-simple`, `whisper-base`, `Kokoro-82M-ONNX`, `all-MiniLM-L6-v2`, `Qwen2.5-0.5B-Instruct`) shall execute inside dedicated Web Workers so the UI thread remains responsive, targeting real-time pose estimation on WebGPU with automatic WebAssembly CPU fallback.

**Acceptance Criteria:**

## L2-033: Light/Dark Theming & User Media Preferences
**Traces to:** L1-013

The system shall style all views exclusively via semantic CSS custom properties supporting both light and dark themes, while honoring system motion, contrast, and forced-colors preferences.

**Acceptance Criteria:**
1. Given the OS or user selects dark theme (`prefers-color-scheme: dark` or explicit theme toggle), when any page, dialog, or notification renders, then all surfaces, borders, text, and semantic status indicators switch to dark-theme token values while maintaining WCAG AA contrast.
2. Given `prefers-reduced-motion: reduce` is active, when navigating, loading skeletons, or opening dialogs/toasts, then smooth scrolling and non-essential animations/transitions are disabled.
3. Given `prefers-contrast: more` or `forced-colors: active` is enabled, when any screen renders, then borders, focus outlines, and interactive controls remain clearly distinguishable.

## L2-034: WCAG 2.2 AA Accessibility Compliance
**Traces to:** L1-013

All pages, dialogs, and notifications shall conform to WCAG 2.2 AA for contrast, semantic structure, keyboard navigation, focus management, and assistive technology announcements.

**Acceptance Criteria:**
1. Given any page in light or dark theme, when contrast ratios are measured, then normal text achieves >= 4.5:1 and large text/UI components achieve >= 3:1 against their background surfaces.
2. Given any page loads, when navigating by keyboard (`Tab` / `Shift+Tab`), then the first focusable element is a `Skip to content` link targeting `#main`, all interactive controls are reachable in logical DOM order with visible focus rings, and semantic landmarks (`<header>`, `<nav>`, `<main>`, `<aside>`) are properly labeled.
3. Given any modal dialog (`end-workout`, `pair-device`, `remove-model`, `verse-search`, `chrome-flags`) opens, when active, then background content is marked `inert` and `aria-hidden="true"`, focus moves into the dialog, `Escape` dismisses the dialog, and closing restores focus to the triggering control.
4. Given a toast notification, system status banner, live rep count update, or form validation error occurs, when rendered, then it is announced to screen readers via appropriate ARIA roles (`role="alert"`, `role="status"`, or `aria-live`) without stealing keyboard focus unexpectedly.
